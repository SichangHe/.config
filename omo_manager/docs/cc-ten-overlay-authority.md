# Ten-page unaccepted overlay authority (design only)

(authored by agents unless marked 🧑)

No protected verifier, signing key, installer, nonce store, manager GO, or production writer is installed by this document. The scorer's signed verdict has `overlay_authorized=false`; it proves reviewed scores, not permission to publish. The CC owner may prepare and test an unsigned request in its two owned `dw5` files, but may not sign, consume a nonce, or publish.

## Exact request and authority boundary

The CC owner constructs UTF-8 sorted-key compact JSON with one trailing newline and an exact, versioned key set. Reject duplicate JSON keys, extra fields, booleans in numeric fields, noncanonical encoding and unknown schema versions. All digests are lowercase SHA-256 of bytes; no path is trusted as a digest. The read-only caller may `lstat` the destination parent but that is only a snapshot, not authority. The unsigned request is exactly:

```json
{"schema_version":1,"operation":"unaccepted-overlay-only","nonce":"<64 lowercase hex>","destination":"<exact approved absolute path>","parent":{"path":"<exact approved absolute path>","device":66307,"inode":85749570,"uid":30033,"gid":1014,"mode_octal":"2700"},"code":{"commit":"<40 lowercase hex>","source_sha256":"<64 lowercase hex>","test_sha256":"<64 lowercase hex>"},"inputs":{"plan_sha256":"<64 lowercase hex>","manifest_sha256":"<64 lowercase hex>","contract_sha256":"<64 lowercase hex>","ledger_sha256":"<64 lowercase hex>","attestation_sha256":"<64 lowercase hex>","scorer_verdict_sha256":"<64 lowercase hex>","ordered_results_sha256":"<64 lowercase hex>"},"outputs":[{"name":"source2128-ten-scored-unaccepted.preview.json","size_bytes":20579,"sha256":"<64 lowercase hex>"},{"name":"source2128-ten-scored-associations.preview.json","size_bytes":4799,"sha256":"<64 lowercase hex>"}],"policy":{"scored":true,"accepted":false,"production_supersession_permitted":false,"production_acceptance_permitted":false,"loader_writes_permitted":false,"database_writes_permitted":false,"provider_calls_permitted":false,"scorer_calls_permitted":false}}
```

The displayed parent numbers and output sizes are current reviewed values, not hardcoded proof of future custody; the protected verifier pins and rechecks them. `outputs` order is fixed as displayed. The request must use the exact fixed destination, never a caller-selected replacement path. An external protected nonce issuer supplies the unpredictable 256-bit nonce; CC never mints, reserves, or consumes one. Until such an issuer exists, fixed test nonces are offline fixtures only.

The caller **claims** the concrete JSON fields above; none authenticate itself. No additional interpreter, dependency, launcher, installer, verifier, or manager-GO fields are required in the CC caller schema. Those bytes and their immutable digests belong to the separately protected installation/verifier record, checked independently before any authorization. A regular commit-shaped string is not proof that the claimed commit contains the source/test bytes: the protected verifier must compare Git tree blob bytes to the claimed digests and verify its own installed executable/import chain. The manager GO alone supplies the bounded invocation window. With that separation, the verifier must independently bind:

- `schema_version=1`, `operation="unaccepted-overlay-only"`, the externally issued 32-byte hexadecimal `nonce`, and the separate manager GO window checked against trusted time
- exact absolute destination and two fixed basenames; pinned parent and ancestor device/inode/UID/GID/mode; destination must be absent, not a symlink or conflicting stage
- exact reviewed Git commit and full source/test blob digests from the caller, plus separately protected installation pins for any executable, interpreter, dependency and verifier bytes; the executable and import chain must be immutable to UID 30033
- frozen plan, ten-input manifest, contract, scorer ledger, scorer attestation, scorer-signed verdict, and ordered receipt-chain byte digests; the existing verdict must still say `overlay_authorized=false`
- the two canonical output sizes and SHA-256 digests, with the association file binding the overlay digest, and exactly ten unique scored-but-unaccepted pages; acceptance, loader, DB, provider, and further scoring permission are all `false`

An independent reviewer under a principal distinct from UID 30033 verifies the input and output bytes, then signs `b"cc-unaccepted-overlay-review/v1\0" + canonical_request` with an Ed25519 private key inaccessible to the CC owner, config's current UID, and the verifier. The reviewer-signed record contains the full request and detached signature; the verifier's installed public key and approved reviewer identity are protected from UID 30033. Config:1 owns only this offline interface design until a separate installer and reviewer are identified.

The DW manager's distinct one-use GO binds the **digest of the complete reviewer-signed record**, the same nonce, exact destination and outputs, one writer identity and bounded invocation window, and only this operation. A protected GO issuer must authenticate the manager's actual approval and sign `b"cc-unaccepted-overlay-manager-go/v1\0" + canonical_go` with a separate key unavailable to UID 30033. A plain manager-authored file or signature using a key readable by the CC owner is not independent authorization. No issuer/key custody or manager-authentication channel has yet been identified.

## Proposed one-use verification sequence

1. A distinct-UID installer pins immutable verifier, interpreter, dependency, public-key and ancestor bytes, creates a nonce-journal directory that UID 30033 cannot modify, and controls the approval channel. Existing config and CC trees do not satisfy this trust boundary.
2. The verifier accepts one unsigned CC request plus reviewer signature and protected manager GO via authenticated IPC, not by trusting CC-supplied paths or environment. It checks exact schemas, both signatures, distinct issuers, window/nonce and operation; it independently hashes pinned inputs and reconstructed canonical outputs. The CC owner only invokes this interface; it never receives signer keys.
3. Before any staging write, the verifier atomically creates and fsyncs an exclusive nonce+request+GO digest receipt under its protected journal. Any existing or ambiguous receipt fails closed; expiry does not make a consumed nonce reusable. Pin the parent by FD, recheck the full identity chain, inventory destination/stages and verify sole-writer custody before proceeding.
4. A separately reviewed executor uses the held parent FD, owner-only stage (mode 0700 after inherited setgid is cleared), exclusive two-file creation and fsync, then `renameat2(RENAME_NOREPLACE)` and parent fsync. The verifier checks output digests, exact two-file inventory and destination identity using held FDs. No accepted-site or production-loader transition is available.
5. A crash or uncertain result after nonce reservation is terminal for that GO: never automatically retry or release the nonce. Independently inspect the protected receipt, held-root identity and any published exact pair; a byte-exact pair may be reconciled read-only, while absent, partial, moved or mismatched output requires new independent authority and a new nonce. No partial-stage deletion is authorized by an ambiguous approval.

Holding a parent FD and `flock` excludes cooperating writers, not an adversarial same-UID process that can rename or edit the mutable runtime tree. An installer must independently protect the path/parent against that adversary or explicitly approve the narrower cooperative-writer threat model. Current outcome: **HOLD** until reviewer, manager GO issuer, protected installer/principal and independent verification of their custody exist. Offline schema tests and published setgid fixes are not a GO.
