🧑 “put task file, without the ‘.md’ in all starter prompts and use that as tags”

A new Codex or OmniGent starter prompt includes `Task tag: TASK_FILE_NAME` (only the final `.md` is removed) and `Task file: TASK_FILE_NAME.md`. Outbound Human mail from an authenticated producer uses `[TASK_FILE_NAME]` when exactly one active current TODO task has that filename and the same owner. Authenticated ordinary replies prefer an explicit task or tmux-window tag over a different old thread owner; untagged replies use the verified thread owner. A unique completed task's tag routes to its current active manager, never the stopped worker. Duplicate, missing, or unresolved names are rejected rather than guessed. Lifecycle commands retain the verified addressed owner rather than retargeting from a changed tag. `[main]` and `[pb]` remain reserved for legacy agent-ID routing, so colliding task names cannot be used as email tags. A main-manager log without a linked task keeps its existing authenticated `[SESSION:WINDOW]` tag. The displayed tag is not proof of pane identity; owner-sensitive helper calls still require their usual producer authentication.

`omo_task.py --task-file TASK.md --workdir DIR --model MODEL --reasoning-effort EFFORT --prompt-file PROMPT` creates and links task files, then starts a host-backed OmniGent session by default. It records the API-returned ID in both `omnigent://SESSION_ID` as `runat` and `session_id`, and delivers the assembled initial prompt through the session API. `--tool` names the actual `antigravity`, `claude`, `codex`, or `cursor` harness. `--tool claude` selects OmniGent even without `--omnigent`, launches Claude Code with `--dangerously-skip-permissions`, and defaults to `claude-opus-5-5` at `low` effort; it has no tmux path. `--tool antigravity` selects OmniGent even without `--omnigent`. Antigravity reasoning effort is `low`, `medium`, or `high`. OmniGent Cursor launch uses the same `--force --sandbox disabled --trust` terminal args and `MODEL-EFFORT` CLI id as tmux Cursor Agent. Native Codex, Antigravity, and Cursor OmniGent producers report with `omo_report.sh` after the live native conversation id exists. The OmniGent loopback server and host are the existing long-lived replacement processes; launch does not start a second listener on `6767`. `--omnigent-host-id` selects a host explicitly; otherwise the sole online host is required. Pass `--tmux --tmux-session SESSION` for the old tmux path: a tmux window with its normal shell, then Codex unless `--tool` overrides the harness. `--tmux-session` without `--omnigent` still selects tmux. Tmux launch and registration require `--tmux-session`. Codex on OmniGent uses the same role model and reasoning effort as tmux Codex; see new-launch defaults below. Already running Codex panes are left running. Manager-ownership migration is the other mode that omits `--tmux-session`.

`--workdir` is mandatory when launching a new worker. Omitted `--model` and `--reasoning-effort` use the harness default. Explicit values override it. Reuse an existing non-human tmux session when practical. A missing session is refused with reuse guidance by default. Pass `--allow-new-tmux-session` only when a new session is genuinely needed; the helper then warns before creating it. `--require-existing-tmux-session` remains accepted for callers that assert the default explicitly, and the two flags are mutually exclusive. A requested `--tmux-window` still requires an existing session. Existing sessions are bound by tmux session ID, and newly created sessions return their session and pane identities for the same post-creation checks. Each new worker window starts in the requested directory through `tmux new-window -c` or `tmux new-session -c`, independent of the session-level starting directory.

Without `--workdir`, `omo_task.py` only registers the task against an exact existing pane named by `--tmux-session` and `--tmux-window`; it does not create a session or window or start a worker. This is also the metadata-only recovery for an existing active task whose canonical TODO row is missing: pass its unchanged task file, exact target, tool, manager target, and manager role, and omit `--workdir`, `--prompt-file`, model, and reasoning options. The helper authenticates a ready or running pane, preserves existing task bytes, and adds the TODO row. `--tool cursor` requires a live `agent` process. `--tool codex` requires a ready or running Codex pane. Missing sessions and missing, shell-only, exited, or error panes are rejected with instructions to use `--workdir`.

`--task-file` identifies the assignment in `omo_task.py`; prompts include only its final filename without `.md`, never the full path. A fresh ordinary Codex launch holds its initial prompt until an exact-pane `/status` query returns the session UUID and that UUID is atomically bound as task-frontmatter `session_id`. A Codex resume writes the already-known UUID during task registration. Tmux Cursor launch identity is not stored because the installed Cursor CLI exposes no equivalent authenticated live-session query; OmniGent supplies the session ID through its API for every supported harness. Workers report from their own tmux pane with `omo_report.sh --alloc-message-file` and `omo_report.sh --status STATUS --message-file FILE`; detached Codex tools can pass their assigned `--task-file TASK.md` to both calls instead of a session ID. Native Codex, Antigravity, and Cursor OmniGent producers can report the same way once the live native conversation id exists.

Use `--tool pcodx` only for a worker that intentionally needs the PCODX CLI wrapper, its scoped `pcodx_partial_compact` MCP tools, and sidecar ledger artifacts under `/tmp/pcodx-runs`; that path records `tool: pcodx` in task frontmatter.

New ordinary worker tasks start with `status: running`; `--is-manager` tasks start with `status: long_running` and `blocked_on: persistent manager role`. New frontmatter also contains `version`, `runat`, `tool`, `managerat`, `is_manager`, and `pending_task_items: []`. `--manager-target TARGET`, or the current `OMO_AGENT_TMUX_TARGET`, supplies `managerat`. After launch, each agent maintains still-open work through the path-opaque `omo_pending.py list|add|replace|remove` interface. Managers retain lifecycle, routing, launch, and closure ownership. Pending-message routing is documented separately in the watcher docs and `supported-delivery.md`.

An existing-shell Codex start clears shell input, runs a short readiness probe in the exact bound pane, and sends the launch command only after its output is visible. A missing probe fails without launching; the manager must confirm the failed sender is terminal and obtain fresh `not_codex` evidence before authorizing another guarded attempt. Fresh prompts whose source plus end-probe budget exceeds the 700-byte visible bound use a private session-bound prompt file and send only its verified pointer after the new session UUID is recorded; shorter prompts retain the guarded full-source handoff. For a fresh replacement whose previous bound session failed, `--compact-initial-handoff --expected-failed-session-id UUID` additionally binds the failed session before that handoff. Neither option resumes the failed session.
Use `--assert-fresh-custody` for a reviewed replacement: bind exact task, ordered queue, blocker, failed session, pane process/start time, source prompt and assembled prompt digests before sending input. Long same-pane rotation prompts use the same session-bound compact handoff, retaining the full Human source. Rotation `--dry-run` never submits `/status`: it uses the stored task session ID or the separately asserted one-use historical ID and fails without either. A one-use old `/status` probe during actual rotation reads composer text only after its new query echo, not from earlier visible prompts; if the query is not visibly returned, the one-use receipt stays uncertain rather than submitting again. Prompt verification matches the whole source and fresh nonce even when Codex hard-wraps a line; a collapsed-paste summary is not proof. 🧑 Text already sitting in the input box is not held for that proof. The helper presses Enter. A pane-scoped initial-prompt guard blocks watcher auto-Enter through a hidden paste or search overlay; it remains set after uncertain submission until a separately reviewed recovery, and clears only after verified submission. Post-submit guard-clear uncertainty preserves the possibly accepted Codex session rather than stopping it. The current UI's warning-only hint immediately below the model footer is not composer input. A dry-run proves these checks only, not a new agent's acceptance; do not retry uncertain delivery.

If a failed prompt handoff has already stopped into an empty shell but left `@omo_initial_prompt_pending`, use `omo_codex_start.py --reconcile-stale-initial-prompt-guard` with exact root, task file, target, task/TODO digests, pane/window IDs, pane PID/start ticks, and the guard's literal value. This operation rejects a live original launcher, changed custody, or a rebound pane and clears only that tmux option; it does not send input, launch a session, or prove the old prompt was accepted. Obtain fresh assertions before any subsequent launch.

Ordinary agent messages and helper-generated pending-watcher/email notices longer than Codex can visibly render are not source proof when the composer shows `[Pasted Content …]`. Messages exceeding the visible 700-byte bound always use a private digest-named file and a short path-and-SHA-256 instruction; short messages retain the ordinary transport. System notices keep their original bytes without an agent envelope. `OMO_MANAGER_COMPACT_DELIVERY=0` skips optional compaction for short messages, never the long-message bound; `1` requires compact-delivery safeguards for every message. The original message remains the dedupe identity; uncertain delivery is never replayed. The sender rejects nonprivate storage, invalid mode values and overly long pointers, and prunes only its own private digest files older than 90 days. An old pointer cannot be assumed recoverable after the retention period.

The stop helper's optional feedback prompt is shorter than the same visible bound. If future wording exceeds it, feedback fails before paste or Enter rather than leaving an unauthenticated collapsed composer; this does not stop or recover any preexisting stuck pane.

Non-submanager VL worker launches, identified by a `vl_` task filename or the `vl` tmux session, require `--manager-target` so reports and watcher status route to the owning VL submanager. Raw `--codex-flag` MCP server config tokens such as `mcp_servers.*` require explicit `--tool pcodx`, so ordinary new Codex agents do not inherit private partial-compaction MCP registration. The exact singleton `--codex-flag=--dangerously-bypass-approvals-and-sandbox` is also supported for an OmniGent Codex launch and records OmniGent's native per-session bypass opt-in; no other raw OmniGent Codex flag is accepted. The MCP tools provide an auditable partial-compaction ledger; they do not rewrite Codex's hidden native transcript.

`getagentsmd get agent_work` plus their output; `--resume-idle` is the no-prompt
recovery exception.
Prompted VL launches add the `getagentsmd get vl_worker` command transcript and

Use paired `--human-email-file FILE --human-email-lines START-END` options with `--prompt-file` on `--workdir` launches to append an inclusive excerpt from human email as the final prompt content. The custom prompt supplies the agent-authored task goal and subgoals; the email options supply the separately labeled human words. Relative `FILE` paths resolve from `ROOT`, and the resolved path must remain inside `ROOT/manager_mail`. The launcher requires both options, validates that the readable file and `END` line exist before mutation, preserves the selected text exactly, and wraps it in `<human_instruction authoritative="true" source="FILE:START-END">` tags. It rejects excerpts containing `</human_instruction>`. The durable task body and worker prompt both retain the root-relative source and selected lines so later agents can distinguish exact human words from manager synthesis. The wrapped runtime excerpt uses an owner-private temporary file across any update retry and is removed after launch verification. These options are not accepted in registration-only, resume-idle, or manager-ownership-migration mode.

Tmux sessions whose names begin with `h` are human-owned. `omo_task.py --workdir` validates the exact requested session and rejects launches into that namespace before creating a session or window or writing task state unless the authoritative `--human-email-file` excerpt contains an unquoted, non-negated explicit launch request naming that exact session on the same line. Accepted wording includes `launch`, `create`, `start`, `open`, or `spawn`, plus requests such as `give me an agent`, `set up an agent`, or `I want/need/would like an agent`. Mentions, quoted requests, and lines containing negation or prohibition do not authorize mutation. Managers must otherwise choose a non-`h` session.
`--allow-new-tmux-session` does not broaden that authority. Creating a missing `h*` session additionally requires direct authoritative text that explicitly creates the exact named session; permission merely to launch an agent there is insufficient. If a newly created session returns invalid identity or its first pane does not become ready, the helper removes only that returned session while its session ID and name still match.
Manager rotation always rejects `h*` targets. Lower-level `omo_codex_start.py` also rejects them except for its documented byte-exact, same-pane `hwl:3` restart authorization; that exception cannot launch, create, move, or recover any other human-owned pane.

`--prompt-file` inside a manager-delegation envelope and stores each selected
human excerpt in a separate authoritative human-instruction envelope. The
launcher rejects a manager prompt containing `<human_instruction` or
`</manager_delegation>` and rejects a human excerpt containing
`</human_instruction>`, so neither source can forge the other's provenance
boundary. Cursor receives the initial prompt as its launch argument. A fresh
ordinary Codex launch starts without the prompt, captures and stores its session
UUID through `/status`, then pastes the prompt into the same authenticated empty
pane and retries a guarded Enter until submission succeeds or the pane leaves a
safe Codex state.

Use `--prelaunch-source SCRIPT` when a worker needs launcher-time environment setup. `omo_task.py` sources that readable shell script inside the worker pane before exporting `OMO_AGENT_TMUX_TARGET` and starting the worker.

Transfer an existing task to a different manager with `omo_task.py --root ROOT --task-file TASK.md --migrate-manager-owner --old-manager-target OLD --new-manager-target NEW`. This requires a unique running `is_manager:true` destination task with an exact `TODO current` target, plus a source whose single `managerat` matches `OLD`. It atomically changes only that value; it does not start or verify a live manager pane. Use `--dry-run` before an independently reviewed transfer.

Dry-run launch planning does not acquire the root membership lock. Mutating launch and ownership operations wait at most five seconds for that lock, then fail before mutation with a retryable `task membership is busy` error. This keeps callers responsive while another lifecycle transaction owns root membership.

The helper writes task/TODO state after tmux creates the worker target and before starting the worker, then verifies that the pane leaves the shell. A worker launch failure is explicit but can leave that manager-owned bookkeeping in place for diagnosis or retry. When tmux cannot create the session or window, the error names a private temporary diagnostic file containing the exact failed tmux command, selected tmux environment, task/prompt/workdir state, exit status, stdout, stderr, and any current session windows. For a directory-trust prompt, `omo_task.py` records the newly created pane's exact tmux ID and pre-launch capture, emits a full UUID marker absent from that baseline, and recognizes only Codex's contiguous bottom-anchored `You are in`/warning/choices/confirmation frame. Confirmation also requires exactly one live supported Codex launch below the pinned pane process; new launches use `@openai/codex@latest`, while existing pinned and legacy `@openai/codex` processes remain recognizable. `h*` sessions are never auto-confirmed. Immediately before selecting the default `Yes, continue` choice once, the helper rechecks that process provenance and requires the logical task target to resolve to the same pane ID, then sends Enter to that exact ID. Split-window active-pane changes, stale scrollback, unframed text, registration-only panes, and arbitrary `not_codex` panes cannot authorize confirmation. If Codex stops on its update prompt, the helper presses Enter to run the update, waits for the restart message, and reruns the original launch command once.
