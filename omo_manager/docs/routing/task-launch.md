# task launch helper

`omo_task.py --task-file TASK.md --tmux-session SESSION --workdir DIR --model MODEL --reasoning-effort EFFORT --prompt-file PROMPT` creates and links task files, opens a new tmux window with its normal shell, then starts Codex with the selected model and reasoning effort through `bunx @openai/codex --dangerously-bypass-approvals-and-sandbox`.

`--workdir`, nonempty `--model`, and `--reasoning-effort` are mandatory when launching a new worker. Without `--workdir`, `omo_task.py` only registers the task against an exact existing ready or running Codex pane named by `--tmux-session` and `--tmux-window`; it does not create a window or start Codex. Missing, shell-only, exited, and error panes are rejected with instructions to use `--workdir`.

`--task-file` is manager-side bookkeeping for `omo_task.py`; keep that path out of worker prompts. Workers report from their own tmux pane with `omo_report.sh --alloc-message-file` and `omo_report.sh --status STATUS --message-file FILE`, without `--task-file`, `--root`, `--manager-target`, or other manual route flags.

Use `--tool pcodx` only for a worker that intentionally needs the PCODX CLI wrapper, its scoped `pcodx_partial_compact` MCP tools, and sidecar ledger artifacts under `/tmp/pcodx-runs`; that path records `tool: pcodx` in task frontmatter.

New ordinary worker tasks start with `status: running`; `--is-manager` tasks start with `status: long_running`. New frontmatter also contains `version`, `runat`, `tool`, `managerat`, `is_manager`, and `pending_task_items: []`. `--manager-target TARGET`, or the current `OMO_AGENT_TMUX_TARGET`, supplies `managerat`. After launch, each agent maintains still-open work through the path-opaque `omo_pending.py list|add|replace|remove` interface. Managers retain lifecycle, routing, launch, and closure ownership. Pending-message routing is documented separately in the watcher docs.

Non-submanager VL worker launches, identified by a `vl_` task filename or the `vl` tmux session, require `--manager-target` so reports and watcher status route to the owning VL submanager. Raw `--codex-flag` MCP server config tokens such as `mcp_servers.*` require explicit `--tool pcodx`, so ordinary new Codex agents do not inherit private partial-compaction MCP registration. The MCP tools provide an auditable partial-compaction ledger; they do not rewrite Codex's hidden native transcript.

Every Codex and PCODX launch passes an initial prompt argument and begins it with `WORKER_DEFAULTS.md`, including launches without `--prompt-file`. VL launches add `VL_WORKER_DEFAULTS.md` after the common defaults and still require `--prompt-file` for task-local context. Manager launches selected with `--is-manager` then add `ROOT/MANAGER.md`; the launch fails before task, TODO, or tmux mutation if that file is missing or unreadable. `--prompt-file` content follows these launcher-managed defaults. The complete order is common worker defaults, optional VL defaults, optional manager instructions, custom prompt file, then any authoritative human excerpt.

Use paired `--human-email-file FILE --human-email-lines START-END` options on `--workdir` launches to append an inclusive excerpt from human email as the final prompt content. Relative `FILE` paths resolve from `ROOT`, and the resolved path must remain inside `ROOT/manager_mail`. The launcher requires both options, validates that the readable file and `END` line exist before mutation, preserves the selected text exactly, and wraps it in `<human_instruction authoritative="true">` tags. It rejects excerpts containing `</human_instruction>` and never includes the source path or line range in the worker prompt. It writes the wrapped excerpt to an owner-private temporary file, uses that file across any update retry, and removes it after launch verification. These options are not accepted in registration-only or manager-ownership-migration mode.

Launcher-managed defaults, `MANAGER.md`, and human email excerpts are prompt-only. Task-file bookkeeping remains unchanged: only `--prompt-file` text is written or appended to the task file. The initial prompt is passed as Codex's launch argument, not pasted after a startup sleep or injected into an existing Codex TUI input line.

Use `--prelaunch-source SCRIPT` when a worker needs launcher-time environment setup. `omo_task.py` sources that readable shell script inside the worker pane before exporting `OMO_AGENT_TMUX_TARGET` and starting Codex.

Transfer an existing task to a different manager with `omo_task.py --root ROOT --task-file TASK.md --migrate-manager-owner --old-manager-target OLD --new-manager-target NEW`. This operation requires valid frontmatter whose single `managerat` exactly matches `OLD`, atomically changes only that value, and performs no pane, prompt, status, TODO, or launch action. Add `--dry-run` to validate and preview the change without mutating any file or pane.

The helper writes task/TODO state before starting Codex, then verifies that the pane leaves the shell. A launch failure is explicit but can leave that manager-owned bookkeeping in place for diagnosis or retry. If Codex stops on its update prompt, `omo_task.py` presses Enter to run the update, waits for the restart message, and reruns the original launch command once.

Use `--model MODEL_NAME` for model selection and follow `MANAGER.md` for the current model policy. `--reasoning-effort EFFORT` passes `--config 'model_reasoning_effort="EFFORT"'`; allowed values are `low`, `medium`, `high`, `xhigh`, `max`, and `ultra`. Both model and reasoning effort are emitted explicitly for fresh and resumed Codex and PCODX launches. Use repeatable `--codex-flag` only for unrelated extra Codex argv tokens, for example `--codex-flag=--profile --codex-flag deep-review`; raw `--model...` and `-m...` tokens are rejected. Use `--session-id UUID` to start `codex ... resume UUID` or, with `--tool pcodx`, `pcodx ... resume UUID` instead of a fresh session. Pane 0 is implied.
