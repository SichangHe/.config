# agent report helper

`omo_report.sh` is the agent-to-manager durable path. Normal worker panes do not need a task-file path: use `REPORT_FILE=$(omo_report.sh --alloc-message-file)` to create a private `0600` draft in an owner-only directory, write that file through an editor/file-editing tool or other non-shell text channel, then run `omo_report.sh --status STATUS --message-file "$REPORT_FILE"` to submit it. Status is normalized to `blocked`, `in-progress`, or `done`; legacy `progressing` means `in-progress`.

The work-log root comes from `local.env`/`OMO_WORK_LOGS_ROOT`, with `~/work_logs` as fallback. The task file is inferred from the current tmux pane by matching active `TODO.md` task refs and frontmatter `runat`, including an active task under `previous`. An omitted pane suffix means only pane `.0`. `TODO.md` target annotations limit candidate reads, and each selected candidate's frontmatter must confirm the target. When a reused target has blocked historical matches, the only `running` or `long_running` task is the producer; a sole blocked task remains reportable. Both worker and manager producers route to the unique active manager task whose `runat` matches the producer's `managerat`. Other collisions fail closed. For compatibility, a producer whose named manager has no active task uses the explicit main-manager fallback with a route warning. Manual `--task-file`, `--root`, `--manager-target`, and similar route flags remain unsupported.

The submit path refuses any file named exactly `REPORT` unless its parent directory is private and owner-only, because shared task/workspace `REPORT` paths can submit stale content. It writes a private detailed report artifact under `/tmp/omo-agent-messages-$UID/`, mode `0600`, then appends only a compact `(pending)` block to the target task Markdown file: `(pending)` followed by `(from agent SOURCE /tmp/omo-agent-messages-$UID/FILE.md)`.

`omo_report.sh --describe --status STATUS --message-file FILE` validates and resolves the transaction without writing or creating Python bytecode. Its compact deterministic JSON includes the body digest and size, canonical status, exact route, every receiver temporary, the public files and locks, allocation protocol, atomic manager-file operation, manager-acknowledgment requirement, and receipt support. `transaction.sha256` immutably binds the complete finite private preflight set: the producer and manager records, routing-source snapshots and derived locks, allocation file effect, replay transaction commitment, envelope, acknowledgment ledger and lock, watcher authority lease/completion, receipt/publication, directories, and all producer/watcher atomic-write temporaries. The public binding includes the set counts, owner-prefix byte binding, and allocation-path digest while excluding the body, actual draft path, route inventory, helper internals, and unrelated task records. The accepted private receipt contains the exact bound set for post-validation and may not broaden it.

Submission atomically replaces or creates the routed record with one appended pointer. The immutable envelope authenticates the original owner-byte SHA-256 and length, routed-path digest, and exact one- or two-byte separator. After delivery, `omo_pending_watch.py` accepts only the exact terminal suffix formed by that binding and pointer, writes the original prefix to the one pre-bound temporary, records the locked transition, and atomically restores the owner bytes. It never reconstructs report-owner bytes with line splitting. Changed owner bytes, a nonterminal/stale/duplicate pointer, a legacy envelope without the byte binding, or any temporary residue fails closed without deleting unrelated bytes.

The helper returns `accepted=true` only after that exact restoration and the watcher acknowledgment. Before the envelope or manager pointer is created, the first locked submission exclusively publishes a private `0600` replay transaction commitment containing its complete preflight set and the allocation snapshot read from the held draft descriptor. The preflight also binds the persistent receipt-directory allocation-replay lock, whose name is derived from the absolute held-draft pathname; the durable receipt records its before/after state and exclusive-lock operation. While no receipt exists, a retry with the same immutable report binding must present the same draft pathname, and the object opened at the start of that attempt must match the committed device and inode. That opened object is authoritative through the attempt: later pathname disappearance, unlink/recreate, or rename replacement is ignored and cannot substitute bytes for the held object. A retry that opens a different object already present at the committed pathname fails before envelope, owner, watcher, receipt, publication, or commitment-residue cleanup mutation; the rejected draft remains unmodified and caller-owned. An initial submission similarly commits the object opened at attempt start even if its pathname is rebound later. Only a retry with the same immutable report binding and committed pathname/device/inode binding can finish pending acceptance. That retry reuses the frozen preflight: every routing source remains byte-identical except that an active-manager routing source may be exactly the committed owner bytes, the protocol-derived owner-plus-pointer bytes, or the exact restored owner bytes. It creates no duplicate commitment, envelope, pointer, receipt, or publication, but may resume a missing step after interruption. After exact receipt publication, a retry with the same immutable report binding, including a same-body new private draft, returns that original receipt and publication. A retry with the same immutable report binding and committed pathname/device/inode binding may recover only an exact hard-linked commitment temporary left by interrupted name retirement; a retry that opens a different object cannot clean or replace it. Missing, conflicting, corrupt, or ambiguous pending commitment state fails closed.

Fresh acceptance also requires the matching live kernel lock established by the watcher-consumption path; the watcher transfers it to a bounded immutable helper lease so another watcher process and immediate receipt replay can verify the same event. The lease remains live until exact receipt publication signals release, with a hard crash cap. A restarted watcher deduplicates only a transition with that live authority; dead, bare, legacy, or forged evidence is delivered again or left pending. A self-declared transition/post-state, unlocked witness, acknowledgment paired with an active pointer, or acknowledgment whose post-state differs from the bound original bytes remains unaccepted. The producer helper reads but never creates watcher transition evidence, acquires watcher authority, or clears the pointer. This is the local helper-role boundary: arbitrary same-UID execution that impersonates the watcher role requires a separate operating-system credential boundary. A submission not acknowledged within the bounded wait returns compact body-free JSON with `accepted=false` and creates no acceptance receipt. The public description withholds the ledger path, replay key, route inventory, and exact draft path; their complete set is hash-bound and recorded privately.

Accepted submissions store a full private `0600` receipt and detached publication record under `$XDG_STATE_HOME/omo-manager/report-receipts/`, with `~/.local/state` as fallback. The stable `replay_id` selects them. The `receipt_id` binds accepted UTC time, input digest and size, canonical status, report context, exact route and route evidence, manager acknowledgment, executable identities, the complete preflight transaction set, allocation evidence, exact owner restoration, operations, and before/after side effects. Every declared temporary is terminally absent. The detached publication record captures the receipt file's exact digest, size, inode, ownership, mode, and timestamps without a self-reference; compact stdout returns both IDs and exact receipt/publication states. If publication stops after the receipt commit, a retry with the same immutable report binding validates the receipt and finishes or reconstructs its exact publication record. If the final publication was already renamed, replay re-fsyncs its directory before accepting it. Later retries with the same immutable report binding, including the same body from a new private draft, return the original acceptance bytes.

The shell executes an immutable byte snapshot. The receiver and imported dependencies are compiled from captured bytes, then checked against source before mutation and acceptance. Submission locks and revalidates the bounded route evidence. Validation, route, acknowledgment, side-effect, receipt, or publication failure never returns `accepted=true`.

When a workflow requires explicit batch and attempt bindings, include one unambiguous `batch: VALUE` line and one `attempt: VALUE` line in the private body. The helper binds their safe values in `report_context` without copying other body text; describe reports whether both migration bindings are available.

`SOURCE` is the inferred worker tmux session/window, such as `vl:4`; submission fails if that producer identity is unavailable. The `/tmp` artifact stores a concise sent line, the message SHA-256, the owner-prefix binding, a `message:` separator, and the report body.

The persistent task file stores no `[omo-message-source: ...]`, `(report manager ...)`, `[message-sha256: ...]`, `message-file: ...`, or report body lines for new agent-originated reports. It does not also push directly to the live manager; `omo_pending_watch.py` owns delivery from the durable Markdown block so the file remains the single source of manager notification.

An existing current-format authenticated pointer can be returned as the same accepted report. A historical verbose marker is not sufficient acceptance evidence: a matching unresolved legacy block fails closed without minting a receipt or appending another marker.
