# email idle watcher

(authored by agents unless marked 🧑)

`email_idle_watcher.py` reads the agent Gmail inbox. Untagged and reserved-tag Human mail is written to `manager_mail/UID.txt` and appended as a pending block. Mail whose subject has exactly one leading stable-agent-id tag, such as `[pb] ...` or `[main] ...`, is an AMH candidate: the watcher fetches Gmail thread metadata, and only then may load the AMH bridge. Missing Gmail thread id, unenabled or unsupported agent ids, and new AMH-tagged mail without `--manager-target` stay on the current-manager pending path and do not create an AMH commit. After AMH commits a source, later launch, metadata, or subject-route failure remains AMH replay or manual recovery instead of falling back.

It accepts any subject only from the exact configured human address; split-account mode also requires the Gmail transport sender and SPF identity. Addressed mail for an active task is appended to that task, including `[og:TASK.md]` tags which map through a unique task filename to that task's `runat`. An `[og:TASK.md]` tag that does not uniquely name a task file is left unread. Unaddressed current-manager mail uses explicit `--manager-file`, otherwise the unique active manager task whose frontmatter and active TODO target match `--manager-target`; only absent current ownership falls back to `work_manager_YYYY-MM-DD.md`. This prevents midnight from changing an existing manager's destination. Ambiguous, mismatched, or inactive current owners are rejected. A per-message route or file-write failure leaves that UID unread and retryable without blocking later messages. Fully processed UIDs are not retried unless they are recorded as unaccepted. Processed UNSEEN UIDs are marked SEEN without re-intake. Normal current-manager mail intake is complete once the Markdown pointer is durable, and `omo_pending_watch.py` owns delivery. The email watcher never sends raw `pending: file=...` references for normal mail. AMH-owned mail does not write a `manager_mail` pending block.

A Human reply can request lifecycle handling by starting its body with the case-insensitive command phrase `replace this agent` or `terminate this agent`. `Please` is not part of either recognized command. Matching stops at `agent`: a period is neither required nor matched, and an explanation or signature may follow immediately without a blank line. No synonym, pronoun, or nonleading lifecycle wording creates a review route. The command requires both `Re:` and an exact leading agent target, normally bracketed but also accepting the existing naked-tmux form. Unaddressed, new-message, invalid-metadata, ambiguous-owner, or incomplete-custody cases do not authorize a lifecycle action.

The watcher stores the exact Human email unchanged and appends a temporary `(pending)` transport block to the addressed task. `(for manager)` makes `omo_pending_watch.py` deliver that block to the task's `managerat`; it is not itself a `pending_task_items` entry and is never delivered to the addressed worker. The marker points to the original email and task instead of duplicating long queue or replacement text. The pending watcher clears the transport only through verified delivery; neither the lifecycle request nor the worker queue is added to a manager's `pending_task_items`. A replay upgrades an earlier ordinary worker-directed marker to manager-only transport. The Human email must never default into the addressed task queue.

For an exact authenticated `terminate this agent` or non-main-manager `replace this agent` reply, intake appends the manager transport, then stops only the addressed live Codex pane with an exact pane/process/start-time guard, leaving its task queue and other panes intact. A private one-use receipt is durable before the stop; a started receipt with no confirmed outcome is not replayed automatically. An unrelated child process prevents the stop. The same rule applies to the main-manager pane for termination rather than silently changing the Human's command to review. Main-manager replacement prepares the successor when possible, claims the mail, stops the incumbent, then launches in the same pane under both rotation and target-input locks. Missing successor preflight does not cancel the Human's stop command; the empty pane and one-use receipt remain for reviewed recovery. An uncertain stop or startup does not replay automatically. A crash between stopping and finalizing its stop receipt permits a manager-only recovery marker only if the original pane is now an empty shell and the recorded old process is gone; it never authorizes a second stop or launch.

Managers resolve lifecycle custody but do not report worker progress or completion to the Human. Manager task mail is limited to fixed supported-helper acknowledgements and one direct question on a verified Human thread. A queued system digest is separate and requires a one-use owner-private capability bound to its exact subject and body. Before publishing a worker-lifecycle transport marker, the watcher records its manager, worker, and exact inbound `Message-ID` in private state. A failed marker append removes only guards created by that attempt. The outbound mail helper rejects every manager or worker non-completion reply whose `In-Reply-To` or `References` contains that message. The responsible worker uses its owner-authenticated completion path.

For non-main-manager replacement the watcher stops first, preserves the original Human mail and ordered task queue, and leaves the pane as an empty shell for the responsible manager to launch one successor. Do not call `--rotate-worker` or `--rotate-submanager` on a stopped pane. Verify the one-use stopped receipt and wait for the manager transport marker to be consumed before marking the task `blocked` with `omo_task_status.py`; that helper refuses live markers. Then use the same-pane fresh `omo_codex_start.py --compact-initial-handoff --expected-failed-session-id OLD_UUID --confirm-empty-shell --prompt-file STORED_MAIL` path with current task and TODO custody. `STORED_MAIL` must contain the Human's original words, not a synthesized prompt; an absent old UUID requires separate reviewed recovery rather than guessing one. Main-manager replacement uses the same prepared launch as `omo_manager_rotate.py` after its stop, without handing the request back to the old manager. Managers may independently choose live rotation with its existing source and custody checks. Termination leaves the queue in its task until the manager reassigns its items with the supported task helpers. The main manager may be replaced but never silently reinterpreted as a termination request.

Watcher input recovery serializes every Enter, Escape, and menu-selection key with the same target-input lock used by lifecycle replacement. The public tmux sender holds that lock across its complete inspect, clear, paste, submit, and verification transaction, so direct email delivery cannot overlap pending delivery. Same-thread nested callers reuse the lock; other threads and processes serialize. Each paste and key is guarded by the exact pane, window, target, process id, command, working directory, and kernel process start time; a rebound or reused process id fails closed.

Legacy self-addressed manager-thread replies may end in a final `PWD: NAME` footer and are ignored instead of being surfaced back to the manager as inbound pending work. The watcher recognizes that final unquoted footer and already-sent `tmux` footers; quoted footer text and messages whose display name is `Human` remain eligible as human replies. Split agent-to-human mail omits this footer because it cannot loop into the agent inbox. Ignored legacy self-authored echoes are also excluded from manager-mail threshold counters.

It keeps IMAP IDLE as the push path and runs an unread fallback scan every `--pull-interval-s` seconds, default `5`, so a missed server notification cannot defer intake until the next long poll. It exits after `--idle-exit-after-s` quiet seconds, default `3600`, so the setup supervisor refreshes it. The separate Human-inbox retention check collects counts every `300` seconds in the background, then applies local state changes on the intake thread, so a slow mailbox count cannot block Human-mail intake or race its task-file write. Intake logs correlate the stored source with the message date, copy start, durable pending time, and pending-watcher submission without adding a metadata round trip. One-shot `--once` scans flush the async queue before process exit.

Legacy self-addressed mode retains `[a]` and `[omo_manager]` threshold checks for already-sent mail. Split-account mode watches only the agent inbox; human-mail cleanup remains available explicitly through the separate human mailbox config and `omo_manager_mail_compress.py`.

🧑 Automatic manager-mail cleanup is triggered only by unread manager mail (`--unread-compression-threshold`, default 16), never by total retained Inbox count. `--total-cleanup-threshold` defaults to 0 (disabled). PB digest streams stay excluded from cleanup classification. The 24-hour-volume trigger remains an independent early-warning path, and ordinary Human inbound mail keeps its separate immediate intake path. These triggers only start the documented compression workflow at https://github.com/SichangHe/personal_browser_setup/blob/main/docs/mail_compression/compression.md (owned by Grok Bot "Mailbox compression"); they do not bypass its replacement, review, or recoverable-Trash gates. Watching may also run via that bot's Gmail routine; Mac IDLE watcher may still raise thresholds. If total-count triggering is explicitly re-enabled, a consumed total-cleanup marker rearms on the next retained message, and a done queue-empty reviewed retain-all/no-op result still suppresses growth smaller than eight messages.

Each threshold record has an immutable identity. Private watcher state tracks that identity as `queued`, `consumed-but-execution-blocked`, or `completed`: consuming the pending marker records delivery, not cleanup completion; the record completes only after the corresponding count no longer exceeds its threshold. Nearby pending blocks do not belong to a threshold record unless they immediately contain its exact identity and source marker.

The processed-UID record is authoritative even after its source task is archived. Only UIDs explicitly recorded as unaccepted delivery attempts are retried. UID state is namespaced by agent inbox because Gmail UID numbers are mailbox-local.

New human email pending blocks write `(record and delegate manager_mail/UID.txt)`. Legacy `(from email manager_mail/UID.txt)` and `[source: email manager_mail/UID.txt]` remain recognized for historical duplicate detection but should not be written for new email blocks.

Stored `manager_mail/UID.txt` files keep the body and a normalized subject, omitting redundant self `From`, `Date`, and `UID` headers because the source marker/file name already identify the message. Legacy human `Re: [a] ...` and `Re: [omo_manager] ...` subjects are stored as `Re: ...` so task-file matching sees the same subject shape the manager originally used.

Leading full tmux window or pane subject tags such as `wl:9`, `[pb:1]`, and stacked `Re: wl:9 wl:6 ...` forms are routing metadata and are stripped before storage or pending presentation. Window targets and zero-pane targets are aliases, so `hcfg:1` and `hcfg:1.0` match the same task. An active addressed task receives only `(pending)` and the email source pointer. The watcher does not write delivery-route metadata; `omo_pending_watch.py` chooses `runat` or `managerat` from the task and message content.

`omo_pending_watch.py` remains the durable delivery path for pending Markdown refs.
