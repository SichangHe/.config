# per-agent sent mail

(authored by agents unless marked 🧑)

Primary Human mail sent through `email_me.py` must use the manager-authenticated route; the legacy split-account route is rejected before SMTP. Operational mail with `--non-completion` is accepted only when the helper process descends from the exact selected tmux pane and that target owns the exact active task. A manager may send only a fixed acknowledgement produced by a supported intake helper or one direct question on a verified Human thread; workers report task progress and results. The helpers refuse acknowledgement without its stored source email and convert an initial subject to a reply. A queued system digest uses a separate one-use owner-private capability bound to its exact subject and body. The inbound watcher records each worker-lifecycle email's exact `Message-ID`; non-completion replies from either the responsible manager or worker are rejected when their reply headers contain that message. Completion mail carries a one-use owner authorization that binds its durable claim, sender target, task, subject, and body. The route also uses an owner-only, exact subject-and-body claim for five minutes, so replaying the same system-spam report is an idempotent success instead of a second email. The claim is created only after local validation and is released after a connection or login failure known to precede delivery; failures from the `send_message` boundary retain it because delivery may be uncertain. Different content remains sendable. `OMO_MANAGER_EMAIL_DEDUPE_S` controls the window; guest replies retain their separate obligation pipeline.

Human completion mail additionally uses `omo_completion_email.py --semantic-key SHA256`. A normal worker close finds the newest message sent by that exact worker session, then replies on its verified Human email chain with the exact body `Closed TARGET`; the exact-session proof permits a chain whose earlier ancestor carried another target tag. Missing identity, timestamps, or history and tied last chains stop before email or lifecycle mutation. An ordinary earlier completion cannot satisfy or suppress this close. The exact key is assigned before delivery, contains no inferred or fuzzy text identity, and may be shared by parent and child task routes. Each route must authenticate as its exact task owner. The first durable claim suppresses every later route with that key even when its task, subject, or body differs; an unkeyed CLI completion is rejected. After task bytes change, an unused close claim may be refreshed only when neither its old nor replacement identity has any outbound evidence and the fixed subject and body are unchanged.

`omo_manager_mail_compress.py agent-unread` reads the Human mailbox and lists only mail still unread after the final metadata fetch. It prints no bodies. Gmail's Human-side unread flag is authoritative; sender-side Sent flags are not used.

An unchanged completion claim that failed before delivery can be retried through `omo_completion_email.py --retry-unattempted-claim KEY` with the original semantic key, exact items, evidence, and answer files. First inspect Sent Mail for the failed answer; an existing copy requires no-send reconciliation instead. The retry checks the unchanged task, unique exact claim, original authorization/content, and absence of outbound-use, delivery, reconciliation, or queued evidence. It preserves the original claim and semantic key. The sender atomically consumes the same authorization before SMTP, so competing retries cannot both send. Once `send_message` begins, any error, including an authentication error, retains the used marker and refuses another send. After confirmed delivery, the original pending removal consumes its receipt without sending again.

After a successful send, `email_me.py` checks the exact Gmail thread for earlier unread messages from the same immutable agent session. If the new message is already read or not visible among unread Inbox messages, it resolves that message's thread from the Human mailbox's All Mail, not the Human account's Sent folder. Lookup is read-only. A match prompts the agent to send one replacement retaining everything still needed from those messages and the new message, then use exact supersession IDs and `agent-trash-replaced`. Other threads and older sessions do not trigger the reminder. Missing or ambiguous thread evidence reports that the check is unavailable; it never removes mail automatically.

If the just-sent email explicitly supersedes every older matching unread Message-ID, the reminder asks for cleanup, not another replacement. This prevents a replacement-reminder loop. If Gmail has not exposed the just-sent message yet, the read-only check retries up to three observations with one-second pauses, refreshing Inbox unread state each time. Ambiguous identities or failed searches stop immediately. `--help` only explains cleanup; an actual `agent-trash-replaced` invocation requires the exact guarded inputs and `--yes`.

New mail carries both its tmux target and immutable Codex session UUID. A current session sees its own mail plus legacy same-target mail without a session header. The JSON marks only current-session mail `trashable`; bound mail from an earlier agent that reused the pane is hidden, and legacy mail remains read-only.

Task-name subject tags are recognized for tmux and OmniGent mail only with the exact current session header. Task-tagged replacements must preserve the selected sources' exact task tag as well as the session and supersedes set. `trash-explicit` also preserves task tags in both its initial and final replacement checks; it does not guess a physical target from a task name.

To replace stale unread mail, send the new message with `email_me.py`, passing each source `message_id` back as `--supersedes-message-id`, and retain the printed replacement `Message-ID`. Then run `agent-trash-replaced` with each selected UID, the listed `source_uidvalidity`, that replacement identity, and `--yes`.

The mutation requires every source to remain unread in Inbox, belong to the current exact tmux pane and Codex session, retain its Gmail identity, and be named exactly by the replacement's `X-OMO-Supersedes` headers. The replacement must be newer, exist inside the configured agent-to-Human boundary, and carry the same tmux and session identities. Sources move only to recoverable Gmail Trash; the command never expunges. Explicit mail from another agent or session, legacy mail, read mail, changed mail, ambiguous or unrelated replacements, and stale UID identities are refused.

Before `MOVE`, the helper persists and directory-syncs an owner-only intent containing source identities but no bodies. A repeated identical command reconciles an interrupted move against Inbox and Trash and records a directory-synced terminal outcome. Mixed or missing outcomes refuse further mutation for manual inspection.

`trash-explicit` requires an explicit source-location mode. Reviewed fresh operations use `--strict-fresh`: every bound source must remain in INBOX, and the final combined INBOX fetch must return the exact bound source UIDs plus retained replacements before `MOVE`. A source already in Trash, mixed prior movement, a missing, wrong, or extra fetched UID, or later location drift stops before mutation. `--recover-partial-move` is a separate interrupted-operation recovery contract that reconciles exact bound sources already in Trash and may move only the remaining bound INBOX subset; it must not appear in a fresh reviewed manifest. Receipts record `source_location_mode`.

Executable reviews must bind the complete local Python runtime, not the live source-tree entrypoint. Run `build-runtime-bundle --out /absolute/owner-only/path/helper.pyz` without mailbox access. The helper recursively resolves every statically reachable local Python import, captures one exact byte snapshot, writes those bytes plus a fixed launcher into one deterministic read-only zipapp, and prints its SHA-256. Execute that `.pyz` with the mandatory `trash-explicit --runtime-bundle-sha256 SHA256` argument. Both CLI and direct Python callers refuse a missing digest, source-tree module loader, mutable `argv[0]` substitution, or archive digest drift before opening a mailbox; receipts record `runtime_bundle_sha256`. Bundled Source-1140 validation keeps its trusted host configuration fixed at `~/.config/omo_manager/local.env` and ignores the general `OMO_MANAGER_LOCAL_ENV` override. The deployment lease covers the single immutable `.pyz`; dirty or later-changing source modules cannot change its imported runtime.

Every `--context` value is the complete frozen thread context. The final gate is one explicit ordered state machine on a separate read-only connection: authenticate the mailbox boundary; recheck INBOX UIDVALIDITY; recheck Gmail special-use identities; read every reviewed thread in one batched Trash observation followed by one batched All Mail observation; then make one combined INBOX fetch that authenticates every strict-fresh source (or explicit recovery-mode live subset) and retained replacement by exact UID and Gmail identities, source raw digest, and retained raw digest, body size, and body digest. `MOVE` on the already-selected source connection immediately follows that combined INBOX read; no unrelated mailbox operation intervenes. The receipt records the observations in `final_gate_observations`.

Supply each source as `--source UID:GMAIL-MSGID:GMAIL-THRID:RAW-SHA256:READ-STATE`, where `READ-STATE` is exactly `read` or `unread`. Supply exactly one generic `--retained-replacement UID:GMAIL-MSGID:GMAIL-THRID:RAW-SHA256:BODY-BYTES:BODY-SHA256:READ-STATE` binding per `--replacement-message-id`; this is mandatory for both CLI and direct Python callers and the receipt records the binding count. The final gate rechecks source and retained read/unread state in the combined INBOX fetch immediately before `MOVE`; post-MOVE reconciliation rechecks retained read/unread state and source disposition. The default `final_context=strict` forbids additions; detected addition, removal, location drift, identity drift, content drift, read-state drift, context mismatch, retained-replacement drift, or bound-mailbox change stops the operation before mutation. Existing integrations that intentionally tolerate only additive source-context arrivals must opt in with `--allow-additive-final-context`; source and retained-replacement bindings remain exact.

Generate retained-replacement bindings with the read-only `inspect-explicit --uids UID --task-id TASK` command. For every selected UID it prints a complete `retained_replacement=...` value ready for the corresponding `--retained-replacement` argument. Its `BODY-BYTES` and `BODY-SHA256` are computed from the decoded message body encoded as UTF-8—the exact representation used by the final gate—not from the human-readable export block printed below it. Re-run inspection immediately before freezing a review; never hand-derive or copy a digest from rendered output.

`--independent-review-file` is required only with `--replacement-not-required`; replacement-based operations bind replacements and any route transition directly in the reviewed `trash-explicit` invocation. After independently reviewing a replacement-free operation, the distinct reviewer must run `build-replacement-free-review` with the exact `--source`, `--context`, Human approval, task identity, source UIDVALIDITY, source-location mode, final-context mode, runtime bundle digest, preparer, and reviewer values. It creates a new owner-only TSV or fails without overwriting an existing file. Pass that file unchanged to `trash-explicit --independent-review-file`. Generated evidence uses `version v1.2.0`, and execution rejects drift in any generated field before mailbox access. Legacy v1.1.0 evidence remains readable for previously reviewed operations; it cannot be generated by the supported workflow.

`FLAGS` values must be exactly `()` or a flat parenthesized list of one or more flag atoms separated by one ASCII space. A flag atom is either an atom keyword or `\` followed by an atom; atoms are visible ASCII and exclude control characters, spaces, `(){}%*"\]`, and inner backslashes. `FLAGS NIL`, missing or duplicate `FLAGS`, quoted strings, nested lists, leading, trailing, doubled, or non-space whitespace, malformed system flags, and atom-special characters are rejected before read-state classification.

IMAP provides no atomic conditional MOVE tied to thread membership. Trash, All Mail, and INBOX are sequential observations, so a nonzero arrival, location, identity, or content-drift race remains after each item's last read and before MOVE. Reversing the thread reads to Trash then All Mail ensures a newly arriving non-Trash member between them is observed by All Mail, and batching all reviewed thread IDs removes per-thread check gaps, but neither measure creates a unified server snapshot. `final_gate_passed=1` means every ordered observation passed; it does not mean the gate was atomic. Receipts report `final_gate_atomic=0` and `residual_arrival_race=nonzero`. After every attempted MOVE outcome—including success, non-OK response, timeout, connection loss, or exception—the helper never retries MOVE and immediately uses its separate read-only connection to attempt source, retained-replacement, and complete-context reconciliation independently, so one failed observation does not suppress the others. `post_move_reconciliation_ran` records whether those attempts started, while `post_move_reconciled` is true only when all three required scopes passed independently of the MOVE outcome. Any uncertain MOVE outcome remains nonzero even if reconciliation fully observes the desired state; ambiguity or a detected race also fails. Reviewed invocations must not claim server-atomic exclusion.
