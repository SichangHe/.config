# per-agent sent mail

`omo_manager_mail_compress.py agent-unread` reads the Human mailbox and lists only mail still unread after the final metadata fetch. It prints no bodies. Gmail's Human-side unread flag is authoritative; sender-side Sent flags are not used.

New mail carries both its tmux target and immutable Codex session UUID. A current session sees its own mail plus legacy same-target mail without a session header. The JSON marks only current-session mail `trashable`; bound mail from an earlier agent that reused the pane is hidden, and legacy mail remains read-only.

To replace stale unread mail, send the new message with `email_me.py`, passing each source `message_id` back as `--supersedes-message-id`, and retain the printed replacement `Message-ID`. Then run `agent-trash-replaced` with each selected UID, the listed `source_uidvalidity`, that replacement identity, and `--yes`.

The mutation requires every source to remain unread in Inbox, belong to the current exact tmux pane and Codex session, retain its Gmail identity, and be named exactly by the replacement's `X-OMO-Supersedes` headers. The replacement must be newer, exist inside the configured agent-to-Human boundary, and carry the same tmux and session identities. Sources move only to recoverable Gmail Trash; the command never expunges. Explicit mail from another agent or session, legacy mail, read mail, changed mail, ambiguous or unrelated replacements, and stale UID identities are refused.

Before `MOVE`, the helper persists and directory-syncs an owner-only intent containing source identities but no bodies. A repeated identical command reconciles an interrupted move against Inbox and Trash and records a directory-synced terminal outcome. Mixed or missing outcomes refuse further mutation for manual inspection.

`trash-explicit` requires an explicit source-location mode. Reviewed fresh operations use `--strict-fresh`: every bound source must remain in INBOX, and the final combined INBOX fetch must return the exact bound source UIDs plus retained replacements before `MOVE`. A source already in Trash, mixed prior movement, a missing, wrong, or extra fetched UID, or later location drift stops before mutation. `--recover-partial-move` is a separate interrupted-operation recovery contract that reconciles exact bound sources already in Trash and may move only the remaining bound INBOX subset; it must not appear in a fresh reviewed manifest. Receipts record `source_location_mode`.

Executable reviews must bind the complete local Python runtime, not the live source-tree entrypoint. Run `build-runtime-bundle --out /absolute/owner-only/path/helper.pyz` without mailbox access. The helper recursively resolves every statically reachable local Python import, captures one exact byte snapshot, writes those bytes plus a fixed launcher into one deterministic read-only zipapp, and prints its SHA-256. Execute that `.pyz` with the mandatory `trash-explicit --runtime-bundle-sha256 SHA256` argument. Both CLI and direct Python callers refuse a missing digest, source-tree module loader, mutable `argv[0]` substitution, or archive digest drift before opening a mailbox; receipts record `runtime_bundle_sha256`. Bundled Source-1140 validation keeps its trusted host configuration fixed at `~/.config/omo_manager/local.env` and ignores the general `OMO_MANAGER_LOCAL_ENV` override. The deployment lease covers the single immutable `.pyz`; dirty or later-changing source modules cannot change its imported runtime.

Every `--context` value is the complete frozen thread context. The final gate is one explicit ordered state machine on a separate read-only connection: authenticate the mailbox boundary; recheck INBOX UIDVALIDITY; recheck Gmail special-use identities; read every reviewed thread in one batched Trash observation followed by one batched All Mail observation; then make one combined INBOX fetch that authenticates every strict-fresh source (or explicit recovery-mode live subset) and retained replacement by exact UID and Gmail identities, source raw digest, and retained raw digest, body size, and body digest. `MOVE` on the already-selected source connection immediately follows that combined INBOX read; no unrelated mailbox operation intervenes. The receipt records the observations in `final_gate_observations`.

Supply exactly one generic `--retained-replacement UID:GMAIL-MSGID:GMAIL-THRID:RAW-SHA256:BODY-BYTES:BODY-SHA256` binding per `--replacement-message-id`; this is mandatory for both CLI and direct Python callers and the receipt records the binding count. The default `final_context=strict` forbids additions; detected addition, removal, location drift, identity drift, content drift, context mismatch, retained-replacement drift, or bound-mailbox change stops the operation before mutation. Existing integrations that intentionally tolerate only additive source-context arrivals must opt in with `--allow-additive-final-context`; source and retained-replacement bindings remain exact.

IMAP provides no atomic conditional MOVE tied to thread membership. Trash, All Mail, and INBOX are sequential observations, so a nonzero arrival, location, identity, or content-drift race remains after each item's last read and before MOVE. Reversing the thread reads to Trash then All Mail ensures a newly arriving non-Trash member between them is observed by All Mail, and batching all reviewed thread IDs removes per-thread check gaps, but neither measure creates a unified server snapshot. `final_gate_passed=1` means every ordered observation passed; it does not mean the gate was atomic. Receipts report `final_gate_atomic=0` and `residual_arrival_race=nonzero`. After every attempted MOVE outcome—including success, non-OK response, timeout, connection loss, or exception—the helper never retries MOVE and immediately uses its separate read-only connection to attempt source, retained-replacement, and complete-context reconciliation independently, so one failed observation does not suppress the others. `post_move_reconciliation_ran` records whether those attempts started, while `post_move_reconciled` is true only when all three required scopes passed independently of the MOVE outcome. Any uncertain MOVE outcome remains nonzero even if reconciliation fully observes the desired state; ambiguity or a detected race also fails. Reviewed invocations must not claim server-atomic exclusion.
